# 設計書：ツキ付き麻雀道場（仮称）

最終更新: 2026-10-07（Phase 1 を実装：一人練習・ツキ補正・牌効率コーチ・点数計算ラボ）

この文書は、作るものと作り方の約束をまとめたものです。フェーズが進むたびに更新します。

---

## 1. 目的

友人と卓を囲んで楽しく打てるレベルになるための、自分専用の学習アプリ。

- 本や動画ではなく、CPU との実戦を通して役・点数計算・戦術を学ぶ。
- 初心者のうちは役がほとんど成立しないので、配牌とツモの「引きの良さ」を人為的に上げ、
  いろいろな役を実際に成立させながら定義のレベルで理解する。
- 上達に合わせて補正を下げ、最後は補正 0（通常の麻雀）で打つ。

出発点は「牌の種類、4 面子 1 雀頭、ポン・チー・リーチの基本」まで。役は一部、点数計算と戦術はこれから。

## 2. 守ること

1. **間違いを教えない。** 点数・符・翻・向聴数・受け入れ枚数・役の成否・危険度の根拠は、すべてエンジンが計算する。
   AI（LLM）は、その結果を文章にすることと自由質問に答えることだけを担う。
2. **山は物理的に正しい。** 赤ドラを含む 136 枚の山を実際に作り、補正は並べ替えだけで行う。
3. **補正を隠さない。** 補正値を常に表示し、補正によるツモは記録に残す。補正 0 の成績を実力として分けて見せる。
4. **スマホ縦画面を最優先。** Streamlit Community Cloud の無料枠で動かす。
5. **エンジンは Streamlit に依存しない。** 純粋な Python にして、pytest でテストする。
6. **同じ局面を再現できる。** 乱数はシードで決まり、局面は「シード＋行動の記録」から作り直せる。
7. **AI のキーが無くても全機能が動く。**

### データの流れ

牌をタップ → 行動 → `game` が状態を進める → `analysis` と `scoring` が事実データを作る →
表と図は事実データをそのまま描く。文章はテンプレートか LLM が同じ事実データから作る。

### 3 つの柱

- **局面は「ルール設定＋シード＋行動の記録」から再生できる。**
  牌譜、局面の再現、局後の振り返り、通信が切れたあとの復帰が、同じ仕組みで済む。
- **和了の解説は、表示のたびにライブラリと突き合わせる。**
  自前で全分解を列挙して途中計算を組み立てる。最終の翻・符・点数がライブラリと食い違ったら、
  ライブラリの値だけを表示して不整合を知らせる。誤った内訳は見せない。
- **乱数は「山」「補正」「CPU」の 3 系統に分ける。**
  同じシードなら補正を変えても元の山は同じ。補正で牌を入れ替えるときは、入れ替える前にそこにあった牌を記録して、画面で見せる。
  並べ替えは自前で実装し、Python のバージョンが変わっても同じ山になることをテストで固定する。

## 5. ツキ補正

### 山の表現

山は牌ID 0〜135 を並べた順列。位置の役割は固定（`engine/wall.py`）。

| 位置 | 枚数 | 役割 |
|---|---|---|
| 0〜51 | 52 | 配牌（13 枚 × 4 人。親から順） |
| 52〜121 | 70 | ツモ山 |
| 122〜125 | 4 | 嶺上牌 |
| 126〜130 | 5 | ドラ表示牌（最初の 1 枚＋カンドラ 4 枚） |
| 131〜135 | 5 | 裏ドラ表示牌 |

52 ＋ 70 ＋ 4 ＋ 5 ＋ 5 ＝ 136。

補正で行う操作は「まだ誰にも見えていない 2 か所の入れ替え」だけ。順列は順列のままなので、
同じ牌が 5 枚になることも、存在しない牌が出ることも原理的に起きない。
既定では王牌と他家の配牌には触れない（ドラ・嶺上牌・他家の手は元のシャッフルのまま）。

山に対して補正ができる操作は 2 つだけにしてある（`Wall.permute` と `Wall.swap_live`）。どちらも、
王牌の位置・すでにツモった位置・配り終えたあとの配牌には使えず、牌の集まりが変わる指定は断る。

### 配牌の補正（`engine/luck.py` の `improve_deal`）

自分の 13 枚とツモ山 70 枚の計 83 枚だけを並べ直した候補を N 通り作り、いちばん良いものを採用する。

- スライダー s（0〜100）に対して N ＝ 256^(s/100) を四捨五入。s ＝ 0 で N ＝ 1（何もしない）、25 で 4、50 で 16、75 で 64、100 で 256。
  ただし s が 0 でなければ、N は必ず 2 以上にする。式のままだと s ＝ 1〜7 は N ＝ 1 に丸まり、
  「補正あり」と表示して成績も分けるのに、実際は何も起きない、という食い違いになるため。
- 選び方：向聴数がいちばん小さい候補。同じ向聴数の候補が複数あれば「受け入れ枚数＋役の見込みの点」が大きいもの。
  役の見込みの点は、役牌の対子・刻子、ドラと赤 5、断么九・一色手・対子手の見え方を足した目安（`hand_prospect`）。
- 聴牌している候補は採用しない（設定で変更可）。だから、最大でも配牌は 1 向聴。
- 候補は毎回同じ順に作る。候補を増やすと、同じシードでは配牌が良くなるか、同じ（悪くはならない）。
- 何が起きたかを記録する（候補の数、元の配牌の向聴数、採用した配牌の向聴数）。局のまとめに表示する。

### ツモの補正（`improve_draw`）

ツモのたびに確率 p で抽選し、当たったら、次のツモ牌が「欲しい牌」でなければ、
これからツモる山の中にある欲しい牌 1 枚と入れ替える（欲しい牌が山に無ければ何もしない）。

- p はスライダーの値から決める：0 → 0、25 → 0.05、50 → 0.12、75 → 0.25、100 → 0.60（あいだは直線）。
  ツモの補正は少しで強く効くので、低い側を細かく割り当てている。
- 欲しい牌：いまは「向聴数を進める牌」（聴牌していれば、あがり牌）。
  役に近づく牌を優先する重みと、高目の優先は、Phase 2 の役指定練習で入れる。
- 入れ替えたツモは「入れ替える前に、その位置にあった牌」と一緒に記録する。画面では、ツモ牌の下に ★ を付け、
  「入れ替えなければ ○○ を引いていました」と出す（設定で消せる）。
  この牌は、その前の入れ替えで動いてきた牌のこともある。だから「素のシャッフルでのツモ牌」とは限らない（そうは書かない）。
- リーチのあとは自動でツモ切りになる。そのあいだに補正で引き寄せた牌にも、局の結果の画面で ★ を付ける。
- 抽選の乱数は（シード, 何回目のツモか）で決まる。確率を上げると、当たるツモは増えるだけで減らない。
- **ツモの補正があると、同じ番号の局でも、切り方によってツモが変わる。** 欲しい牌は手牌から決まるので、
  手牌が違えば、入れ替える牌も違ってくる。同じ番号で必ず同じになるのは配牌まで。ツモまで同じになるのは、ツモの補正が 0 のとき。
  画面の説明も、そう書いている。
- 嶺上ツモには補正をかけない。

### 補正 0 の保証

補正 0 では、乱数を作らず、山にも触れない。山は素のシャッフルと完全に一致する。テストで次を確かめている。

- 補正 0 で最後まで打った局の山が、どの時点でも素のシャッフルと同じ並びで、ツモが山の順番どおりであること。
  そのあいだに使った乱数が「自風を決める」ぶんだけであること。
- 補正 0 の配牌 5,000 局の向聴数の分布が、別の乱数（Python 標準の乱数）で 200 万回測った分布と一致すること
  （カイ二乗検定。自由度 5、上側 0.1% 点）。同じ検定に「弱」（候補 4 個）の配牌をかけると、はっきり外れることも確かめている。
- 2 万局ぶんの山に、配牌の並べ替えとツモの入れ替えをくり返しても、山がいつも 136 枚の牌をちょうど 1 枚ずつ含み、
  王牌とほかの席の配牌が変わらず、すでにツモった牌があとから変わらないこと。

### 測った効き具合（一人練習のエンジンでの実測）

`tools/measure_luck.py` で測った。各 300 局。打ち手は機械的（いつもコーチのおすすめを切り、聴牌したら必ずリーチ）。
あがりはツモだけで、1 局は 18 回のツモまで。

| 段階 | 値 | 配牌の候補数 N | ツモ補正の確率 p | 配牌の平均向聴数 | あがり率 | あがったときの平均巡目 | 入れ替えたツモの割合 |
|---|---|---|---|---|---|---|---|
| なし | 0 | 1 | 0 | 3.55 | 16% | 14.1 | 0% |
| 弱 | 25 | 4 | 0.05 | 2.73 | 48% | 12.6 | 4% |
| 中 | 50 | 16 | 0.12 | 2.09 | 73% | 11.2 | 9% |
| 強 | 75 | 64 | 0.25 | 1.63 | 95% | 7.8 | 19% |
| 最大 | 100 | 256 | 0.60 | 1.23 | 96% | 3.6 | 43% |

4 人対局では他家のあがりで局が終わるぶん下がる。Phase 3（CPU 戦）で測り直す。

分かったこと:

1. **ツモ補正は少しで強く効く。** だから、スライダーは低い側を細かく割り当てている。
2. **速くあがらせるだけでは役が増えない。** どの段階でも、あがりの中身はほぼ「立直・門前清自摸和」で、
   平和 2〜3 割、断么九 1 割、七対子 1 割、一盃口 5% ほど。三色同順や一気通貫はほとんど出ない。
   いろいろな役を実際に成立させるには、役指定練習（Phase 2）が要る。
   まだ図鑑にスタンプのない役を「今局のテーマ」として自動で選ぶモードも作る。
3. **役指定は候補選びだけでは足りない（設計時の検証）。** 64 候補から選んでも、三色同順に必要な 9 種のうち平均 2.2 種が欠け
   （補正なしは 4.5 種）、国士無双は平均 4.8 向聴（同 8.2）。役指定モードでは「役向聴数」
   （その役の完成形までの距離）を定義し、配牌とツモ山の間で 1 枚ずつ入れ替えて目標の距離まで作り込む。

### そのほか

- 嶺上開花・海底摸月・河底撈魚・槍槓・天和・地和のような偶然役は、補正ではなく専用の出題で体験する。
- CPU 側は同じ仕組みを席ごとに持ち、初期値は 0。
- おまかせモード：直近の打牌評価とドリルの正答率が基準を超えたら 1 段階下げ、下回ったら 1 段階戻す。
- 成績は、補正値と「打つ前のヒントを見たか」をセットで記録する（`engine/records.py`）。集計は、この条件ごとに行を分ける。
  **「実力」と呼ぶのは、補正 0 で、打つ前のヒントも見ずに打った局だけ。** 補正 0 でも、おすすめを見ながら打った局は別の行にする
  （おすすめをなぞれば良い成績になるので、実力には数えない）。
  「ヒントを見た」は、打つ前のヒントを 1 回でも画面に出した局。切る瞬間の設定では決めない
  （ヒントを見てから設定を切り替えて切っても、ヒントなしの局にはならない）。
  打牌の一致率（いちばん速い打牌を選べた割合）は、ヒントを見た局では出さない。
  やり直した局・番号を指定した局・途中でやめた局は、成績に入れない。CPU 戦では、CPU の強さとルールも一緒に残す。

## 6. 正確さの担保と AI の役割

表示する内容を確かさで 3 層に分け、画面でも区別する。

| 層 | 例 | 出どころ |
|---|---|---|
| ルール上の確定事項 | 和了の可否、役、符、点数、フリテン、役なし | mahjong ライブラリと照合 |
| 数え上げで決まる数値 | 向聴数、受け入れ枚数、見えている枚数、引ける確率 | エンジンの厳密な計算 |
| 判断 | 推奨打牌、鳴き、リーチ、押し引き | 経験則。基準と根拠の数値を必ず添え、速度・打点・安全度で推奨が割れるときは割れていると表示する |

- LLM に渡すのは事実データだけ。返ってきた文章に、事実データにない点・符・翻・枚数や牌名が含まれていたら
  捨てて、テンプレート解説に戻す。表と図は LLM を通さず、エンジンの値を直接描く。
- 役図鑑とドリルの例題は、成立例・ひっかけ例の全件をテストでライブラリにかけ、
  「成立する／しない」が記載どおりか自動で確かめる。図鑑の翻数もライブラリの値と突き合わせる。
- 用語の由来と漢字の意味は機械では検証できない。出典つきの下書きを出して確認を受け、
  はっきりしないものは「諸説あり」と書く。

### 判定ライブラリ（mahjong 2.0.0）について確かめたこと

- ライブラリを呼ぶのは 2 か所だけ：点数の判定（`engine/scoring/judge.py`）と向聴数（`engine/analysis/shanten.py`）。
- 計算は `HandCalculator.estimate_hand_value` などで行う。結果に符の内訳は含まれるが、
  どの分解を採用したかは含まれない。分解の列挙は自前で行う。
- 牌ID 16・52・88（各色の 5 の 1 枚目）が赤5。ライブラリの文字列変換では「5」がこの ID になるので、
  手牌を文字で書くときは必ず `engine.tiles.parse_tiles` を通す。
- 連風牌の雀頭は常に 4 符で、切り替えがない。2 符の設定は符計算の部品を直接呼んで組み立てる。
- 設定オブジェクトを使い回すと、前の計算結果のドラ翻数が後から書き換わる。毎回新しく作り、結果はすぐ写し取る。
- 門前ロンの符は「副底 20 ＋門前加符 10」をまとめた 30 として返る。解説では分けて見せる。
- 速さ：向聴数 1 回 約 40 マイクロ秒、打牌 14 通り × ツモ 34 種の受け入れ表が 1 局面 約 19 ミリ秒（開発環境）。
- 手の読み方を「翻 → 符」の大きい順で選ぶ。役満は 13 翻として数えるので、ドラが多くて 14 翻以上になる
  別の読み方（数え役満。数え役満なしの設定では三倍満）があると、役満の読み方より先に選んでしまう。
  例：333萬 333444555筒 44索 のツモ（四暗刻）を、345筒 × 3 の一盃口＋ドラ 8 と読む。
  `judge.py` は、役満でない 13 翻以上の結果が返ったら、ドラと偶然役を外してもう一度判定し、
  役満の読み方があればそちらを採る。ランダムな 40 万局の照合で見つけた（発生は 3 局）。
- 「ダブル役満なし」の設定でも、返ってくる役の番号はダブル役満用のまま（翻数だけが 13 になる）。

### 和了の解説の作り方（Phase 1 で実装）

1. **読み方を全部挙げる。** 「分解（どの牌をどの面子・雀頭と見るか）」×「和了牌がどのブロックに入ったか」。
   同じ分解でも、和了牌の入り方で待ちの形（両面か単騎か、など）が変わるので、別の読み方として数える。
2. **読み方ごとに計算する。** 符の内訳（1 行ずつ）、役（成立条件を 1 つずつ確かめ、どの牌で満たしたかを残す）、
   ドラ、点数の式、支払い。
3. **高点法で 1 つ選ぶ。** 並べ方は 受け取る点 → 役満かどうか → 翻 → 符 → 切り上げ前の符。
   ライブラリと違って「点」で比べる（役満と数え役満が同点なら、役満の読み方を採る）。
4. **ライブラリと突き合わせる。** 翻・符・役（名前と翻数）・役満の倍数・支払い・本場・供託・合計・ドラの翻数。
   1 つでも違えば内訳を出さず、ライブラリの値だけを表示する。

テストでの保証:

- 手で計算した期待値との照合（利用者が指定した全項目。`tests/test_scoring_table.py`）。
- ランダムな和了形でのライブラリとの照合。入力は役満・槓子・清一色・同じ順子 3〜4 組などが多く出るように偏らせる。
  ふだんのテストは 5,000 局、開発時は 40 万局で食い違いなし。
- 「惜しかった役」は次のどれかに限る：条件が 1 つだけ足りない／雀頭の役牌があと 1 枚／ツモなら成立／
  面子か雀頭が 1 つ違えば成立。多くても 3 つ。
- 流派で結果が変わる手（喰いタン、切り上げ満貫、連風牌の雀頭、ダブル役満、数え役満、赤ドラ）には、
  「ルールによって変わるところ」を必ず添える。

### 一人練習と牌効率コーチの作り方（Phase 1 で実装）

**一人練習（`engine/practice.py`）**

- 配牌 13 枚 → ツモ → 1 枚切る、を最大 18 回（4 人で打つときの 1 人ぶん。70 枚 ÷ 4 ≒ 18）。
- あがりはツモだけ。鳴きとカンは無いので、手はいつも門前。あがったときの解説は、点数計算（`engine/scoring`）をそのまま使う。
- リーチは、切っても聴牌が残る牌でだけ宣言できる。リーチのあとは、あがり牌が来るまで自動でツモ切り。
  ダブル立直・一発・天和・地和は、条件を満たせば付く。海底摸月は付けない（18 枚目は、本当の山の最後の牌ではないため）。
- 状態は「設定（シード・補正・ルール）＋行動の列」から作り直せる。ブラウザに残すのは、この小さな記録だけ。

**コーチ（`engine/coach.py`）** ― いまは速さ（牌効率）だけを見る。役・打点・守備は Phase 3 で加える。

| 出すもの | 中身 |
|---|---|
| 向聴数 | 判定ライブラリの値。意味（聴牌まであと何枚）を添える |
| 打牌候補の表 | 切る牌ごとに、切ったあとの向聴数と、受け入れ（有効牌の種類・残り枚数）。残り枚数は、自分の手牌・河・ドラ表示牌に見えている牌を引いて数える |
| おすすめ | 向聴数がいちばん小さく、受け入れ枚数がいちばん多い牌。同じなら、まずドラ（赤 5 を含む）を手放さない牌。それも同じなら、使いにくい牌から（客風 → 役牌 → 1・9 → 2・8 → 3〜7） |
| 引ける確率 | 次のツモで引く確率 ＝ 有効牌の枚数 ÷ 見えていない枚数。残りのツモのうちに 1 回以上引く確率も出す（補正なしの麻雀での値） |
| 手牌の分け方 | 面子・対子・搭子・孤立牌に色分けした図。向聴数の式（8 − 2 × 面子 − 搭子 − 対子）も出す。式がライブラリの値と合わない手（同じ牌 4 枚持ち）では、式を出さない |
| 聴牌したときの待ち | 待ち牌ごとの残り枚数と、ツモであがったときの点数（リーチする／しない）。点数は点数計算の結果そのもの |
| 切った牌の評価 | おすすめと比べて、同じ速さ／受け入れが少ない／聴牌から遠ざかる／有効牌が残っていない形／あがりの見送り、のどれか。理由（増える有効牌、くずしたまとまり）を添える |

決めごと:

- **受け入れが 0 枚の形は、向聴数が 1 つ大きいものとして比べる。** 待ち牌がすべて見えている聴牌（空聴）は、何を引いてもあがれない。
  有効牌が残っている 1 向聴のほうを勧める。このとき、案内と表に出す向聴数は「おすすめを切ったあと」のもの（1 向聴）にそろえ、
  「聴牌にもとれるが、待ち牌が残っていない」と添える。形の上の向聴数（聴牌）だけを出すと、案内と表が食い違う。
- **ドラの数え方は「その種類を切るとき、実際に手放す牌」で決める。** 赤 5 を 1 枚だけ持っている 5 は、切ればドラを手放す。
  赤でない 5 も持っていれば、切るのはそちらなので、手放さない。こう数えないと、同じ速さの候補の中から赤 5 をおすすめに選び、
  切ったあとで「ドラは残したほうがよい」と言う、という食い違いが起きる（点検で見つかり、直した）。
- **遠ざかった理由で名指しするまとまりは、損が小さいほう。** 同じ牌が順子と対子の両方に入っている手（567 と 55 など）で
  その牌を切ると、順子は残せるので、くずれるのは対子。「567 がくずれる」とは言わない。
- **「同じ受け入れ」と言うのは、有効牌の中身まで同じときだけ。** 残り枚数の合計が同じで中身が違うときは、「枚数が同じ」と言う。
- **最後の打牌は、聴牌で終われるかどうかだけで比べる。** このあとツモが無いので、受け入れの広さは関係ない。
  聴牌にとれない手は、どれを切っても同じ（成績でも減点しない）。
- **赤 5 とドラの注意。** 同じ速さの候補があるのにドラを切ったとき、赤でない同じ牌があるのに赤 5 を切ったときは、ひとこと添える。
  おすすめの牌を切って、この注意が出ることはない（テストで確かめている）。
- **あがれるときは、リーチのボタンを出さない。** あがりを見送ってリーチする打ち方は、エンジンでは受け付けるが、押し間違いを防ぐため画面では出さない。
- 評価の文章は、数値から機械的に組み立てる。AI（LLM）は使っていない。
- いまのコーチが扱うのは、門前の 14 枚だけ。鳴いた手（14 − 3n 枚）は、副露の情報を持たせる必要があるので、鳴きを実装するとき（Phase 4）に広げる。

## 8. 画面

### 牌の操作（Phase 0 で実装・検証）

- 14 枚を 1 列に並べると、幅 390px の画面で 1 枚 約 24px になり、指で押し分けられない。
- 7 枚 × 2 段にすると 1 枚 47 × 62px（幅 360px の端末で 43 × 57px、320px で 37 × 49px）。
- 押し間違いを防ぐため「選ぶ → 確定」の 2 段階。選んだ牌をもう一度押しても確定できる。
- 確定を送ってから応答が返るまでは押し直せない。8 秒返らなければ押し直せるように戻す。
- 画像が読めないときは文字で表示する。
- Streamlit 標準の部品だけで同じ操作ができる予備の方法も残す。

### 保存と復帰

- Streamlit Community Cloud ではサーバーのファイルが残らず、通信が切れたセッションは一定時間で消える
  （既定 120 秒。設定で 900 秒にしてある）。スマホでは画面ロックやアプリの切り替えで起きやすい。
  公開版で測ると、通信を 168 秒切っても同じセッションに戻れて、次の打牌がそのまま通った
  （既定の 120 秒なら消えている長さなので、900 秒の設定は Community Cloud でも効いている）。
  16 分 49 秒切ったあとは、セッションが作り直されていて、つなぎ直すと、ブラウザの記録から同じ局面に戻り
  （「ブラウザに残っていた記録から再開したものです」と表示）、その次の打牌が通った。
- そこで、局面の小さな記録（シードと行動の列）を利用者のブラウザに置き、開き直したら再生して続きから始める。
- 進捗（スタンプ、ドリルの履歴、成績）も同じ場所に自動保存する。ブラウザ内保存は端末ごとで、消えることもある
  （Safari は、Safari を使った日が 7 日ぶん過ぎるあいだ一度も操作しなかったサイトの保存を消す。ホーム画面に追加したものは別に数える）。
  だから JSON の書き出し・読み込みを必ず付ける（Phase 2）。外部ストレージへの差し替えは `ui/` の保存の窓口だけで済むようにする。

ブラウザとのやり取りの決まり（`ui/components/browser_store`。Phase 1 で作り直した）:

- **読むのは、セッションごとに 1 回。** ブラウザの中身をまとめて送ってもらい、あとはサーバー側の控えを読む。
  この 1 回は「1 回きりの値」で送る。「持ち続ける値」で送ると、画面を更新するたびにブラウザが全部を送り直す
  （成績が 500 件あると、1 回の操作ごとに上り 約 119 KB になっていた）。
- **書くのは、番号を付けた操作を 1 件ずつ。** 操作は 3 種類：置き換える（set）、消す（remove）、配列の末尾に 1 件足す（append）。
  ブラウザは番号で「もう済ませた操作」を見分けるので、同じ操作が 2 回届いても結果は変わらない。
  「済ませた」という報告は、6 件たまったときと、書けなかったときだけ送る（報告のたびに、画面の再実行が 1 回起きるため）。
- **成績は「末尾に 1 件足す」で書く。** 全体を書き直さないので、記録が増えても通信量が増えない
  （成績 500 件のとき、1 回の操作で 下り 約 31〜71 KB・上り 約 1 KB。作り直す前は 下り 約 270 KB・上り 約 119 KB）。
  足す先は「いまブラウザに入っている配列」なので、2 つのタブで打っても、互いの記録を消さない。
- **ページを開いたまま、通信が長く切れたとき。** サーバー側のセッションは消えていて、戻ってきて最初に押した操作は届かない
  （届け先のセッションが、もう無い）。新しいセッションは合言葉が違うので、ブラウザ側が気づいて中身を送り直し、
  サーバーは記録から局を作り直す。画面は 1 秒ほどで切れる前の局面に戻り、
  「通信が切れていたので、続きから再開しました。もう一度操作してください。」と知らせる。
  手牌の部品に渡す番号（`rev`）の出発点も、セッションごとに変える
  （同じ 0 から始めると、部品は「まだ応答が無い」と見なして、送信中のまま止まる）。
- **「保存を使わずに始める」を選んだあとで届いた返事は、使わない。** 途中から保存を始めると、
  ブラウザに残っていた記録を、読まないまま上書きしてしまうため。
- **ブラウザに残っている記録は、壊れていることがある**（古い版の形、途中で切れた書き込み、手で書き換えた値）。
  エンジンの読み込み（`from_save`・`from_dict`）は型と範囲を確かめて `ValueError` にそろえ、画面側はどんな例外も外に出さず、
  読めなければ「記録なし」として新しい局を始める。開くたびにエラーで止まって、直す手段も無い、という状態を作らない。
- **アプリを更新したとき。** `engine/` と `ui/` のモジュールは読み直す（`ui/fresh.py`）が、セッションに入れてあるオブジェクトは
  読み直す前の古いクラスのまま残る。新旧が混ざると、同じはずの値が同じと判定されない
  （実際に、あがった局が流局と表示された）。そこで `app.py` がコードの世代を数え、世代が変わっていたら、
  文字と数だけの控えから、局・打牌の評価・成績を作り直す（`PracticeSession.sync_code`）。

### 和了の解説と点数計算ラボ（Phase 1 で実装）

- 解説は 7 段：① 手牌の読み方 → ② 役 → ③ ドラ → ④ 符 → ⑤ 点数 → ⑥ 誰がいくら払うか → ⑦ 卓での申告。
  いちばん上に、状況と点数のまとめを置く。詳しさは「要点だけ／ふつう／くわしく」の 3 段階。
- 手牌 14 枚は 1 列に並べる（幅 375px で 1 枚 約 23px。表示専用なので押し分けは要らない）。
  分解図は 1 枚 30px で、面子ごとにまとめて折り返す。和了牌には枠を付ける。
- 点数の式は 1 行で書く：「30 符 3 翻・子のロン：30 × 2⁵ ＝ 30 × 32 ＝ 960 → × 4 ＝ 3,840 → 切り上げて 3,900 点」。
- 卓での申告は、発声 → 役 → 点数：「ロン。リーチ・ピンフ・ドラ 1。3900。」
- ラボの手は URL で開ける（`/lab?ex=F-1`、`/lab?kind=fu&n=12345`）。再読み込みしても同じ手に戻る。
- 「先に自分で計算する」を入れると、答えと解説を隠す。Phase 2 で、答えの入力と正答率の記録を足す。
- 手の入力は、いまは文字（mpsz 表記）。牌をタップして組み立てる入力は、希望があれば Phase 2 で足す。

### 一人練習の画面（Phase 1 で実装）

- **手牌とボタンの位置を動かさない。** 上から、状況（場・自風・巡目・ドラ・ツキ補正）→ ひとことの案内 → 手牌 →「この牌を切る」、の順に置く。
  巡ごとに長さが変わるもの（前の打牌の評価、受け入れ表、分解図、河）は、すべてその下に置く。
  - ひとことの案内は、高さを固定する（72px。幅 350px 以下では 96px）。文が 1 行でも 2 行でも、下の手牌は動かない。
  - 「この牌を切る」の段は、いつも 2 段ぶんの高さにする（案内の文の段と、ボタンの段）。
    リーチのボタンが出る巡目でも、牌を選んだときでも、ボタンの位置が変わらない。
  - 実機の画面（幅 375 × 高さ 606px）で測った位置：手牌の上端 273.5px、「この牌を切る」の上端 463.6px・下端 512px。
    ヒントのタイミング 3 通り、どの巡目でも同じ値になることを、ブラウザの通し確認で測っている。最初の画面に収まる。
- **ツキ補正の強さは、いつも状況の中に出す。** 補正で入れ替えたツモには ★ を付け、元のツモ牌も見せる（設定で消せる）。
  リーチのあと自動で進んだあいだのツモも、局の終わりに並べて、入れ替えた牌に ★ を付ける。
- **ヒントのタイミング**は「打つ前に表示」「打った後に答え合わせ」「オフ」。
  打つ前：案内に向聴数とおすすめ、手牌に印（◎ おすすめ、○ 同じ速さ）。打った後：案内に前の打牌の評価、下に前の局面の受け入れ表。
- **表示の量**は「詳しい／ふつう／最小」。最小は案内と評価のひとことだけ。ふつうは表と図を折りたたみで。詳しいは開いた状態で、確率と式の説明も出す。
  「詳しい」に変えたら、その場で折りたたみが開く（折りたたみの名前に表示の量を入れて、出し直している。10 章）。
- 選ぶ形の設定（ヒントのタイミング、表示の量）は、選んであるものをもう一度押しても外れない。
  ツキ補正の段階（なし・弱・中・強・最大）の表示は、2 つのスライダーの値から毎回決め直す。
- **リーチ**は手牌の部品の中で選ぶ。「リーチ」を押すと、切っても聴牌が残る牌だけが明るく残る（オンラインの麻雀と同じ操作）。
  リーチのボタンがあるあいだは、案内文とボタンを別の段にして、牌を選んでもボタンの位置が動かないようにしている。
- 河は、卓と同じく 6 枚ずつ並べる。リーチを宣言した牌は横向きにする。
- 局が終わったら、結果 →「次の局へ」「同じ局をもう一度」→ ツキ補正で起きたこと → 打牌の振り返り → あがりの解説 →「次の局へ」（下にも置く）、の順に出す。
- 新しい局を始めたら、画面のいちばん上までスクロールを戻す（設定の中のボタンは画面の下のほうにあるので、
  戻さないと、始まった局の手牌が見えない）。
- **番号を指定して始める**：入力欄とボタンを 1 つのフォームにする。数字のキーボードが出て、入力してすぐボタンを押しても 1 回で始まる。
  全角の数字も受け付ける。誤りは日本語で知らせる（「番号は、0〜999999 の数字で入れてください。」）。
- **成績の「実力」は、補正 0 で、打つ前のヒントを見ていない局だけ。** 同じ補正でも、ヒントを見た局は別の行に分ける。
  確率は言い切らない（0% と 100% は、「1% 未満」「99% 以上」と書く）。

### そのほかの約束

- 牌は画像で表示する。Unicode の麻雀牌文字は主表示に使わない。
- 数式は Unicode 記号とプレーンテキストで書く。LaTeX 記法は使わない。
- 画面に出す数は、四捨五入で書く（`ui/practice_view.py` の `rounded`）。書式の指定（`f"{x:.1f}"`）に任せると、
  2 進数の誤差と「偶数への丸め」のために、手で計算した値と 1 つずれることがある（3.55 → 3.5、62.5% → 62%）。
- 用語の初出にはルビを付ける。画面を 1 回描くごとに、用語ごとに最初の 1 回だけ（`ui/ruby.py`）。
  読みの表は `engine/terms.py`。エンジンの文章には読みを書き込まない（ルビは画面の仕事）。
  - 文章は、画面の上から順に作る。作る順と見える順が違うと、ルビが 2 回目に出てくるほうに付いてしまう。
  - 折りたたみの中身は、別の範囲として数える（`rb.fork()`）。閉じていると読まれないので、中で振ったルビを
    「もう出てきた」とは数えない。折りたたみの外で先に出た用語は、中ではくり返さない。
  - 入力欄や折りたたみの名前（Streamlit の部品の文字）には、ルビを付けられない。用語が入る名前の前に、ルビ付きの説明を置く。
  - 役の表のように、名前のすぐ横に読みを並べて書いたものは、ルビの代わりに「読みを見せた」と数える。
  - 色の付いた札（「満貫」など）は、札の外側からルビを付ける（内側に入れると、暗い画面で読みが見えなくなる）。
  - 検査：`ui.ruby.missing_ruby` が「初出なのに読みが無い用語」を挙げる。自動テスト（ページの HTML）と
    ブラウザでの通し確認（折りたたみをすべて開いて、画面の上から順に）の両方で、0 件を確かめる。

## 10. 動かして分かった Streamlit の癖（Streamlit 1.65.0）

- ボタンに入れられる画像は文字の高さまで。牌の画像をボタンにするには自作の画面部品が要る。
- 自作部品（カスタムコンポーネント v2）はビルド不要で、枠（iframe）なしで動く。
  部品の JavaScript は、最初の表示と、Python から届くデータが変わったときだけ呼ばれる。
  画面の要素は呼び出しをまたいで残る。
- 部品からの値はコールバックで受ける。そこで状態を進めれば、1 回の再実行で新しい局面が描ける。
- 部品は置くたびに登録する（読み込み時に 1 度だけだと、自動テストで登録が失われる）。
- ページのフォルダ名を `pages/` にすると、`st.navigation` と併用したとき、サーバーの起動直後に
  ページの URL を直接開くと「Page not found」のダイアログが出る。`views/` にして避けた。
- `static/` に置いたファイルは `app/static/...` で配信される（設定で有効化）。
- ページの URL を直接開くと `/ページ名/_stcore/health` などへの 404 が 2 件出るが、
  Streamlit 自身の動作で、害はない。
- **だれも接続していないあいだに書き換わったモジュールは、読み直されない。** ページの本体（`app.py` と `views/`）は
  次の表示で読み直されるが、読み込み済みのモジュール（`engine/` と `ui/`）は古いまま残る。
  Community Cloud への反映はこの状況で起きるので、0.2.0 を公開した直後に
  「新しいページが古い `engine.tiles` を呼んで TypeError」になった。
  対策として、`app.py` の先頭で自作モジュールのファイルの更新時刻を調べ、変わっていたら読み込み済みの
  自作モジュールを捨てる（`ui/fresh.py`）。手元で同じ状況を再現し、再起動なしで直ることを確かめた。
  画面部品の HTML/CSS/JS を変えた場合も、同じ仕組みで新しい内容に入れ替わる
  （Streamlit は「登録済みの部品を上書きした」という注意を記録するだけ）。
- 描かなかった入力欄（ウィジェット）の値は、その実行のあと消える。途中で `st.stop()` すると、
  その下の入力欄の値が失われる。入力に誤りがあっても入力欄は最後まで描く。
  表示していないあいだも覚えておきたい値は、入力欄とは別の名前でも持つ。
- 入力欄の値は、その入力欄を描く前でも `st.session_state` から読める。だから
  「まとめを上に、条件を変える欄を下に」置ける。
- `st.html` に渡した HTML の中の `<style>` は当てにしない。共通のスタイルは `ui/layout.py` で 1 か所に入れる。
- スマホの幅では `st.columns` は縦に積まれる。横に並べたいものは `st.container(horizontal=True)` に入れる。
- 画面なしのテスト（AppTest）では、`st.html` の中身は `at.get("html")` の `proto.body` で読める。
  ブラウザでのテストでは、`st.segmented_control` の選択肢は `role="radio"` で探す。
- **折りたたみ（`st.expander`）には `key` を付ける。** 付けないと、その上にある要素の数が変わったとき
  （打牌のたびに評価が増える、設定を変えて表示が変わる、など）、開いていた折りたたみが閉じてしまう。
  設定の折りたたみの中で設定を変えると、その折りたたみ自身が閉じる、という形で気づいた。`key` を付ければ開いたまま残る。
- 自作部品は既定で Shadow DOM の中に置かれる（`isolate_styles=True`）。ページ側のスタイルは部品の中に届かないので、
  部品のスタイルは部品の CSS に書く。ブラウザのテストの CSS セレクタは、Shadow DOM の中まで届く。
- Community Cloud は、アプリを枠（iframe）の中に入れて表示する。アプリ本体だけを開く URL は `…streamlit.app/~/+/ページ名`。
  公開版の文字を機械的に読むときは、こちらを開く。
- 開発用の環境（コンテナ）からは、通信の制約で公開版を開けない（Streamlit が使う WebSocket が通らない）。
  公開版の確認は、利用者の Chrome を経由して行う。
- **自作部品から Python へ送る値は 2 種類ある。** 「持ち続ける値」（`setStateValue`）は、再実行のたびにブラウザから送り直される。
  「1 回きりの値」（`setTriggerValue`）は、送った 1 回だけ届く。大きなデータを 1 度渡すだけなら、1 回きりの値を使う。
- **セッションが消えたあとの最初の操作は、届かない。** 新しいセッションには、ボタンや部品のコールバックの登録がまだ無いので、
  操作は捨てられ、スクリプトが最初から走るだけになる。このとき、ブラウザ側の部品は前のセッションの続きのつもりでいる
  （「中身はもう送った」「送信中」）。サーバーが新しくなったことを、部品に渡すデータ（合言葉、番号の出発点）で伝える必要がある。
- モジュールを読み直しても、セッションに入れてあるオブジェクトは古いクラスのまま残る。新しいコードとの比較
  （列挙型の `==`、`isinstance`）が食い違う。セッションには、文字と数だけの控えも持っておき、そこから作り直す。
- `st.expander` の開閉は、`key` が同じあいだ、ブラウザ側が覚えている。あとから `expanded=` を変えても反映されない。
  開いた状態と閉じた状態を切り替えて出し直したいときは、`key` を変える。開閉だけでは、再実行は起きない。
- `st.segmented_control` は、選んであるものをもう一度押すと選択が外れる（値が `None` になる）。
  必ず 1 つ選ばせるなら `required=True`。
- `st.text_input` の `required=True` や `validate=` は、案内が英語で、しかも小さな印の中に隠れる。入力の確かめは自前でする。
  `type="phone"` にすると、スマホで数字のキーボードが出る。入力欄とボタンをフォーム（`st.form`）に入れると、
  入力してすぐボタンを押しても、値とボタンが 1 回で届く（フォームの外では、1 回目のタップは入力の確定に使われる）。
- 見出し（`st.subheader`）には、ルビを入れられない。ルビ付きの見出しは `st.html` で `<h3>` を書き、大きさを Streamlit の見出しに合わせる。
- `st.toast` の文が長いと、途中で切れて「view more」が付く。短く書く。
- スライダーの上で指を縦に動かしても、ページはスクロールしない（スライダーが指の動きを受け取る）。スライダーの外を持って動かす。
- 画面なしのテスト（AppTest）は、`max_chars` を超える入力を黙って切り詰める。長すぎる入力の確かめは、関数の単体テストでする。
- 利用者の Chrome を経由して公開版を確かめるとき、そのタブが裏に回っていると、手牌の部品があるページでは
  画面写真が撮れないことがある（裏のタブでは、画像の展開が進まない）。文字と DOM を読んで確かめる。
- 手元で「枠の中のアプリ」を再現するときは、外側のページも同じ `localhost` から出す
  （よそのサイトのページから `localhost` を枠に入れると、Chrome が読み込みを止める）。
